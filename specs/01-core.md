# Core: scanning and CodeGraph

Deterministic evidence only: same tree, same text. No LLM in the core.

## Scanning

- **SCAN-01** MUST — read requirements from `- **ABC-12** MUST|SHOULD|MAY — text` bullets in the specs folder and its subfolders, joining a wrapped bullet's continuation lines.
- **SCAN-02** MUST — find test tags `[ABC-12]` (also `[ABC-12, ABC-14]`) in the test folders.
- **SCAN-03** MUST — count a source citation only when the ID follows a line-comment marker; block comments and code are not scanned.
- **SCAN-04** MUST — give each requirement one state: `tested`, `src-only`, `none`, `manual` or `later`; struck-out bullets are retired and never due.
- **SCAN-05** MUST — print the same text for the same tree: no clocks, randomness or map-order dependence.
- **SCAN-06** SHOULD — take folders, extensions and regexes from an optional `spec17.json`, and fall back to defaults when it is missing.
- **SCAN-07** MUST — report invalid test tags (unknown, retired, comment-only, disabled, no assertion) and dangling citations as problems to judge, not as verdicts.
- **SCAN-35** SHOULD — recognize bracketed tags in comments attached directly above or inside a detected test, including intervening annotations, and assess disabled and assertion evidence against that test. Use a matching CodeGraph function or method range when available and the index is not older than the test file; otherwise detect common test-body endings for Python, Ruby, Lua, Erlang, Visual Basic, Pascal and SQL, including PostgreSQL named dollar quotes and nested blocks, ignoring braces in common quoted strings and comments. A test must not acquire tags or assertions from the next test.
- **SCAN-36** SHOULD — distinguish `comment-tagged` IDs attached to detected tests in the report from `comment-only` IDs without a detected test; the former is evidence to review, not an invalid test verdict.
- **SCAN-37** SHOULD — detect Swift test declarations with backticked names, without claiming XCTest will discover or run them.
- **SCAN-38** SHOULD — provide worked `case`, `call` and `inline` profile examples in `spec17.example.json`.
- **SCAN-08** MUST — trace one ID to its spec text, tests and code citations.
- **SCAN-09** SHOULD — detect what `spec17.json` leaves out: the specs folder (`specs/`, `spec/`, `docs/specs/`, `openspec/specs/`, `.kiro/specs/` and the like, a generic `docs/` only with a requirement bullet), and the source and test folders, extensions and test-file pattern of the dominant ecosystem, from the CodeGraph file list when an index exists, else from the repo's files.
- **SCAN-11** SHOULD — also accept the common spec spellings: `*`, `+` and numbered lists, a plain, `**bold**` or `` `code` `` ID with an optional colon, the level anywhere in the line (`MUST`, `SHOULD`, `MAY`, `SHALL`), and `| ID | MUST | text |` table rows.
- **SCAN-23** SHOULD — also accept a requirement that opens a block: a `### ABC-12: title` heading (up to the next heading) or a `**ABC-12** title` paragraph, with the level anywhere in the block, EARS `shall` in lower case too; dotted IDs (`AC-1.2`); and no "has no MUST/SHOULD/MAY" issue for a line that mentions an ID defined elsewhere (a cross-reference table, a review note).
- **SCAN-24** SHOULD — match IDs by the rules of `spec_format.toml`, several at once: a prefix of 2–10 capitals and digits with `-` and up to five digits, dotted parts allowed (`FR-001`, `RULE-1`, `AC-1.2`), or with `_` (`REQ_001`, `REQ_001.2`); a well-known token (`UTF-8`, `ISO-8601`, `SHA-256`, `TLS-1.3`: the `not_id` shapes) is never a requirement, a test tag or a citation, while an ID with the same prefix (`HTTP-01`) still is.
- **SCAN-25** SHOULD — read every spec, test and source file as UTF-8: a byte-order mark is skipped, non-ASCII text is kept as written, and the Unicode hyphens editors paste (U+2010, U+2011) read as `-` throughout, so an ID written with one still matches.
- **SCAN-26** SHOULD — with no `specs` in `spec17.json`, scan every dedicated spec folder that holds markdown, not only the first one found: `specs/`, `spec/` and the other names of SCAN-09, OpenSpec's `openspec/specs/` and each in-flight change's `openspec/changes/*/specs/` (never `archive/`), and Superpowers' `docs/superpowers/specs/` (not its `plans/`); a generic `docs/` only when none of them holds a requirement line; and when no place does, any markdown file with a requirement line, a heading or paragraph block (SCAN-23) too.
- **SCAN-27** SHOULD — read OpenSpec deltas: `### Requirement: ABC-12 name` with its SHALL is a requirement; one under `## REMOVED Requirements` is retired; a change's definition of a requirement replaces the one in `openspec/specs/` without a duplicate issue; a `### Requirement` heading with no ID (OpenSpec, Kiro) is a spec issue and not counted, since no test can cite it.
- **SCAN-12** SHOULD — find specs beyond a specs folder of bullets: IDs of up to four digits (`REQ-0001`), single-file specs (`SPEC.md`, `REQUIREMENTS.md`, also in `docs/`, or a `specs` setting that names a file), and, when nothing else holds a requirement line, any markdown file of the repo that does.
- **SCAN-13** SHOULD — treat a markdown link `[ABC-12](path.md)` to an existing markdown file, and a decision-folder file `0003-title.md` (`adr/`, `decisions/` …), as a reference doc with that ID: state `ref`, never due, with the files that link to it in its trace; report a link to a missing file as a spec issue.
- **SCAN-14** SHOULD — list the test cases of the test files (a Rust `#[test]`, a JUnit `@Test`, a Python `def test_`, a JS `it(`, a Go `func Test` and the like, or the `case` regex of a `spec17.json` profile) with the requirement IDs tagged on each, grouped by module; a marker inside a string literal is not a case. Detected, not run: it says nothing about passing.
- **SCAN-10** MUST — follow a symlink only when it resolves inside the repo root or a path listed in the `ALLOWED_PATHS` environment variable.
- **SCAN-16** SHOULD — list the requirements a git diff touches (`status --changed <ref>`): staged, unstaged and untracked files, mapped from their changed line ranges to the spec lines and cited code they hit. A pure deletion marks the line it sat before.
- **SCAN-17** SHOULD — print consecutive IDs of a list as one range (`DOC-01..03`), with the others separated by commas, in the summary and problem lines.
- **SCAN-19** SHOULD — give the unified diff of one changed file (against a ref or in one commit; a rename shows both paths, an untracked file is all additions, cut at 3000 lines) for the files `changes` lists, and under each hunk the requirements it touches (SCAN-18); refuse any other path, and a ref or sha that looks like a git option.
- **SCAN-18** SHOULD — list what changed as `changes`: against a git ref (`ref`, HEAD by default) or in one commit (`commit`, against its first parent), every changed file with what happened to it (`added`, `modified`, `deleted`, `renamed` with its old path), where (`staged`, `unstaged`, `both`, `untracked`, or `committed` for what is in the compared commits) and its kind (`spec`, `test`, `src`), and the requirements the changed lines touch, down to the line: a hunk in its bullet (`spec`: added, edited, removed: a removed bullet is listed as deleted), in a test that carries its `[ID]` tag (`test`) or in the code unit its `// (ID)` citation sits on (`src`; the whole file when the language has no braces). `staged` narrows to the index, `include_untracked=false` leaves untracked files out, `ignore_whitespace` leaves out changes that only touch whitespace, `show_ignored` adds the files `.aiignore`, `.spec17ignore` and `.agents` hide, `show_all` adds the files spec17 does not scan (kind `other`). Evidence of what was edited, not that it is done.
- **SCAN-21** MUST — refuse a `specs`, `src`, `tests` or `codegraph` path in `spec17.json` that leaves the repo (an absolute path, `..`, a symlink out), unless it resolves into `ALLOWED_PATHS`, so a repo's config cannot make spec17 read other files.
- **SCAN-22** SHOULD — in `changes`, also list a requirement when a changed source file is one its tagged tests reach through the CodeGraph index (GRAPH-04), noted as reached by a test, not cited.
- **SCAN-20** SHOULD — list the commits of a branch that are not on the base branch (`history`: main or master by default, newest first, with the number of uncommitted files), so each one can be explained with `changes commit=<sha>`; on the base branch itself it lists the latest commits. A commit that changes no file the filters show (whitespace-only changes, ignored files, files spec17 does not scan) is left out.
- **SCAN-28** MUST — open a repo with no specs without an error: zero requirements and spec files, while the sources, tests and modules are still scanned, and `status` with no filter lists nothing instead of failing, while the `report` text says "no specs found" in a note, so zeros are not read as success; a `specs` path in `spec17.json` that does not exist counts as no specs. The root is the nearest ancestor with specs, else the nearest git work tree, else (only with `--root`) that folder; with none of these it is still an error, so spec17 never walks `~` or `/` on its own.
- **SCAN-30** SHOULD — name, for each requirement, the newest commit that touched its lines (`git blame` of its spec file, newest author time over the requirement's block): its sha, author, date and subject, so the specification shows who changed it last: `blame_commits`. A requirement with an uncommitted line, or in a file git does not track, has none. Evidence of when and by whom the text last changed, not that anyone reviewed it.
- **SCAN-34** SHOULD — take ecosystem profiles from `profiles` in `spec17.json`, each shaped like a `[[profile]]` of `profiles.toml`: one named like a built-in profile changes only the fields it sets, any other adds an ecosystem without a rebuild. Each of `decl`, `assert`, `off`, `test` and `case` accepts one regex or an ordered list of regexes; use the first matching pattern for each input, with capture group 1 of a matching `decl` as the name. A bad regex in one is an error, and the retired top-level `comment`, `decl`, `assert` and `off` are an error that points to `profiles`.
- **SCAN-33** SHOULD — read each file with the ecosystem profile of its extension (comment markers, declaration, assertion and switched-off regexes), and a file no profile knows with the dominant one; in a mixed repo a Rust `#[doc = "[ID]"]` tag is then not a Python `#` comment, and a Python `assert` counts.
- **SCAN-32** SHOULD — in `changes`, `diff` and `status --changed`, list a requirement as added, edited or changed only when its text differs from the base version of the file (the ref, or the first parent of an explained commit, through the old path of a rename): a requirement's bullet, tagged test or cited code unit that reads the same once whitespace and line wrapping are collapsed (a rewrap, a re-indent, an edit of its neighbour in the same hunk) is left out. A new file, a new unit and a removed one still count.
- **SCAN-31** SHOULD — name the commit (sha, author, date, subject) that last changed given lines of a scanned spec, test or source file, by `git blame` (`blame_at`), refusing any other path; a test is asked for by the line of its tag or name. Evidence of who last touched that line, not of the whole test.
- **SCAN-29** SHOULD — `trace` names, for each source citation, the declaration it belongs to: a comment line that leads into a declaration (only comment, doc or attribute lines between) belongs to that declaration, any other comment to the nearest one above, so a `// (ID)` placed above a doc comment is not credited to the function before it.

## CodeGraph

- **SCAN-15** MUST — leave out what the repo's `.aiignore` and `.spec17ignore` (gitignore syntax) hide, and always `.agents`, from every file walk and every file the CodeGraph index lists, so they reach no test, source, module or spec list.
- **GRAPH-01** MUST — open the CodeGraph index read-only, with all SQL in `core/src/codegraph.rs`.
- **GRAPH-02** MUST — turn a schema the code does not know into a typed error shown as "not checked", never a panic.
- **GRAPH-03** MUST — treat a missing index as "not checked", not as an error: indexing is the user's decision.
- **GRAPH-05** SHOULD — group the repo's files into modules (the nearest folder with a build manifest, else the folder above `src`), count a file as a test file only when it is test-named or in a tests folder that is not also a source folder (inline unit tests stay source), and from the index count each module's symbols and the dependencies between modules.
- **GRAPH-04** SHOULD — link tests to code through the index.
- **GRAPH-06** SHOULD — list each module's source files (`sources`), so the dashboard can show them with or without a requirement.
