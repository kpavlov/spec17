# Dashboard

- **WEB-01** MUST — the URL is the view: tab, selected requirement, spec file, code path and line, filters; every navigation (a click on a tab, row or link) updates `window.location` and adds a history entry, while typing in a filter replaces it, so back, forward, reload and shared links work; inside an MCP host iframe, which has no URL of its own, the view still changes. (manual)
- **WEB-02** MUST — build to one `index.html`, which the binary embeds and MCP hosts get as the dashboard resource. (manual)
- **WEB-03** MUST — never claim a requirement is implemented or a test passes: evidence, not truth. (manual)
- **WEB-04** SHOULD — link every test, citation and spec location to the file viewer or spec it names. (manual)
- **WEB-05** SHOULD — open on the dashboard (the whole-project status) at `/`, and offer a modules tab (a table, and a page per module with its symbols, dependencies, dependents and detected tests) and a tests tab (every detected test by module and file, with the requirement IDs tagged on it, filterable by module, tagged or untagged, and text), both labelled detected, not run. (manual)
- **WEB-06** SHOULD — refresh itself when the repo changes: on the server's `resources/updated` push (throttled to one reload per 2 seconds), and by polling every 30 seconds as a fallback (reloading only when the report differs). (manual)
- **WEB-07** MAY — show the server connection as a small dot next to the title: green connected, red disconnected, grey until known, with the state as its tooltip. (manual)
- **WEB-08** SHOULD — the file viewer highlights syntax by file extension and offers, next to the file name, copy path, open in an editor (the URL scheme of a JetBrains IDE, VS Code and forks, Zed, Sublime, TextMate or Xcode) and a wrap toggle; the last editor and the wrap state are remembered in the browser; the page uses the full width and never scrolls sideways (long code scrolls inside its box). (manual)
- **WEB-09** SHOULD — show the modules and their dependencies as a graph (a list/graph switch on the Modules page, remembered in localStorage): a node per module with area proportional to its symbols, a directed edge per module dependency weighted by its edge count, laid out by a force simulation (repulsion between modules, gravity to the centre, a hard core so modules never overlap) and drawn on a canvas with straight arrows, with zoom, pan, drag, node hover and tooltip (WEB-56), a text filter, and a click through to the module page. It needs the CodeGraph index and says so without one. (manual)
- **WEB-10** SHOULD — offer an ignore button on each module of the modules list that, after a confirm, sets the module hidden through `module` (API-11) and reloads the dashboard. (manual)
- **WEB-11** SHOULD — add a "show hidden" checkbox to the modules filter (only when some module is hidden, remembered in localStorage) that lists the hidden modules, dimmed, each with an unhide button that sets it shown again through `module` (API-12) and reloads the dashboard. (manual)
- **WEB-12** SHOULD — move the selected row of the requirements and tests lists with the up and down arrow keys (not in the requirements table of the Changes page, where the arrows scroll; the preview follows; the first press selects the first row, and the selection replaces the history entry instead of adding one). (manual)
- **WEB-13** SHOULD — give the requirements, tests and modules tables sortable column headers (click: ascending, descending, file order), and group the requirements by ID prefix (`AIN-03`, `ARCH-03`) when there is more than one prefix, in collapsible groups that start expanded with the collapsed ones remembered per root in IndexedDB (collapsing or expanding changes only that group in the stored record, so groups another tab saved meanwhile are kept); a collapsed group is one stop of the arrow keys of WEB-12, and while a group is selected left and right collapse and expand it, and up from the first requirement of a group selects the group, down from the last one selects the next group, and up and down move to the previous or next group (its last or first requirement when expanded, the group itself when collapsed). (manual)
- **WEB-14** SHOULD — filter requirements by state and level, with evidence hints and `none` and `src-only` first; group SHALL and reference documents under other. Keep selected choices available even when absent and count choices against the other filters. (manual)
- **WEB-15** SHOULD — show the requirements and tests lists, each with its preview, as two panes that scroll on their own (the page does not scroll with them, and the header row of the list stays put): the list on the left and the preview on the right on wide screens, with a button next to the filter that switches to the list on top and the preview below, remembered in localStorage; narrow screens always stack them. The preview pane stays in place when the selection changes (the previous content stays, dimmed, until the next one loads; the Requirements list uses the full width with no preview until a requirement is selected), and a splitter between the panes resizes them by drag or by arrow keys (15% to 85%; double-click or Home resets), with its position remembered in localStorage (per page kind) next to the orientation, which is one choice for both lists. (manual)
- **WEB-16** SHOULD — show "N of M" and a "Clear filters" link next to the filter while any filter is active; row borders show evidence state, while priority and effort badges are colored by value (WEB-57). (manual)
- **WEB-17** SHOULD — drive the requirements filters from the keyboard when no field has focus: `1`–`7` pick a state, `S`, `L`, `P`, `E`, `C`, and `R` step through state, level, priority, effort, changes, and reviewed choices (`⇧` steps back), `0` clears every filter, `/` focuses search and `F` opens the filter menu. (manual)
- **WEB-18** SHOULD — navigate from a sidebar: the destinations grouped (Overview, Browse, Gaps) with an icon and a label each, and a control at the bottom that collapses it to an icon rail (tooltips keep the names; the choice is remembered in localStorage, and narrow screens start collapsed). On phones it becomes a strip of icons above the page. (manual)
- **WEB-19** SHOULD — on the Tests page show every detected test as a row (grouped by module, with its requirement IDs and its location) and, in the preview, the selected test: its name, location and module, the requirements it is tagged with (ID and text), and the source lines around it; the selection is in the URL (`?path=…&line=…`) and Esc clears it; with no test selected the list uses the full width and there is no preview pane. A tag is evidence, not proof that the test passes. (manual)
- **WEB-20** SHOULD — on the Requirements page offer a View switch, list or documents (`?view=docs`): the documents view renders the chosen spec file (picked from a list of the files) in a single scrollable document pane, marks each requirement ID with its state, and scrolls to the requirement named in the URL. (manual)

(manual)
- **WEB-22** SHOULD — mark what the working tree changed in the requirements, tests, specs and modules views (change reasons in the row of each affected requirement, `✎ spec edited`, `✎ src changed`, …, and on a file or module row a pill saying whether it is added, modified, deleted or renamed, or committed) and give each a "changed only" filter with its count, kept in the URL (`?changed=1`). (manual)
- **WEB-23** SHOULD — offer a Changes page that shows every change in one place: the changed files, each marked added, modified, deleted or renamed (and whether staged), linked to the file viewer, the requirements they may affect (with their state), and the affected tests, specs and modules linking to their filtered views, with switches for staged only and untracked files; it says "working tree clean" when nothing changed and "not checked" without git. (manual)
- **WEB-25** SHOULD — in a preview pane of a changed item (a requirement, a test, a spec file, the code viewer) offer an actual / diff switch: "diff" shows what exactly changed against HEAD, per file, with added and removed lines coloured and the hunk headers dimmed; the last choice is remembered in localStorage, and an item with no change shows the actual view without the switch. (manual)
- **WEB-26** SHOULD — let the Changes page choose what is compared (HEAD, the base branch, or one commit from the history of the commits not on the base branch, each marked committed), switch whitespace-only changes, ignored files and files spec17 does not scan on, show a deleted requirement as deleted and a rename with its old path, and name under each diff hunk the requirements it touches. - **WEB-24** SHOULD — show a Changes card on the dashboard (changed files by added, modified and deleted, requirements affected and how many of them have no test) that links to the Changes page, with the affected count as a badge on the tab. (manual)
- **WEB-27** MUST — on connect ask `doctor` and `install_status`: Settings renders from those alone, never behind the scan, and a failed scan shows its error with a link to Settings instead of "Scanning…". (manual)
- **WEB-28** SHOULD — with no requirements, show a "no requirements yet" card on the dashboard (what a requirement line looks like, a link to Settings) in place of the 0% hero, still show the changes, the modules and the counts of source files, test files and detected tests, and say on the Requirements page that nothing was found. (manual)
