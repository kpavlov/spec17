# Dashboard

- **WEB-01** MUST — the URL is the view: tab, selected requirement, spec file, code path and line, filters; every navigation (a click on a tab, row or link) updates `window.location` and adds a history entry, while typing in a filter replaces it, so back, forward, reload and shared links work; inside an MCP host iframe, which has no URL of its own, the view still changes. (manual)
- **WEB-02** MUST — build to one `index.html`, which the binary embeds and MCP hosts get as the dashboard resource. (manual)
- **WEB-03** MUST — never claim a requirement is implemented or a test passes: evidence, not truth. (manual)
- **WEB-05** SHOULD — open on the dashboard (the whole-project status) at `/`, and offer a modules tab (a table, and a page per module with its symbols, dependencies, dependents and detected tests) and a tests tab (every detected test by module and file, with the requirement IDs tagged on it, filterable by module, tagged or untagged, and text), both labelled detected, not run. (manual)
- **WEB-04** SHOULD — link every test, citation and spec location to the file viewer or spec it names. (manual)
- **WEB-06** SHOULD — refresh itself when the repo changes: on the server's `resources/updated` push (throttled to one reload per 2 seconds), and by polling every 30 seconds as a fallback (reloading only when the report differs). (manual)
- **WEB-07** MAY — show the server connection as a small dot next to the title: green connected, red disconnected, grey until known, with the state as its tooltip. (manual)
- **WEB-08** SHOULD — the file viewer highlights syntax by file extension and offers, next to the file name, copy path, open in an editor (the URL scheme of a JetBrains IDE, VS Code and forks, Zed, Sublime, TextMate or Xcode) and a wrap toggle; the last editor and the wrap state are remembered in the browser; the page uses the full width and never scrolls sideways (long code scrolls inside its box). (manual)
- **WEB-09** SHOULD — show the modules and their dependencies as a graph (a list/graph switch on the Modules page, remembered in localStorage): a node per module with area proportional to its symbols, a directed edge per module dependency weighted by its edge count, laid out by a force simulation (repulsion between modules, gravity to the centre, a hard core so modules never overlap) and drawn on a canvas with straight arrows, with zoom, pan, drag, hover highlighting of a node's neighbours, a text filter, and a click through to the module page. It needs the CodeGraph index and says so without one. (manual)
- **WEB-10** SHOULD — offer an ignore button on each module of the modules list that, after a confirm, sets the module hidden through `module` (API-11) and reloads the dashboard. (manual)
- **WEB-11** SHOULD — add a "show hidden" checkbox to the modules filter (only when some module is hidden, remembered in localStorage) that lists the hidden modules, dimmed, each with an unhide button that sets it shown again through `module` (API-12) and reloads the dashboard. (manual)
- **WEB-12** SHOULD — move the selected row of the requirements and tests lists with the up and down arrow keys (not in the requirements table of the Changes page, where the arrows scroll; the preview follows; the first press selects the first row, and the selection replaces the history entry instead of adding one). (manual)
- **WEB-13** SHOULD — give the requirements, tests and modules tables sortable column headers (click: ascending, descending, file order), and group the requirements by ID prefix (`AIN-03`, `ARCH-03`) when there is more than one prefix, in collapsible groups that start expanded with the collapsed ones remembered per root in IndexedDB; a collapsed group is one stop of the arrow keys of WEB-12, and while a group is selected left and right collapse and expand it, and up from the first requirement of a group selects the group, down from the last one selects the next group, and up and down move to the previous or next group (its last or first requirement when expanded, the group itself when collapsed). (manual)
- **WEB-14** SHOULD — filter the requirements by state and by level (MUST, SHOULD, MAY, and "other" for SHALL and reference docs when there are any) with two labelled segmented controls that each start with "all" (and, when git gives commits, a third, Reviewed, WEB-35), ordered so that `none` and `src-only` come first, with a hint on each state saying what the scanner saw. Show the choices present in the unfiltered list and keep the selected choice available even if it is absent. Each count is what the segment would show given the other filters (state, level, text), a visible segment that drops to zero is dimmed, the choice is kept in the URL (`?level=MUST`), and the arrow keys move within a control. (manual)
- **WEB-15** SHOULD — show the requirements and tests lists, each with its preview, as two panes that scroll on their own (the page does not scroll with them, and the header row of the list stays put): the list on the left and the preview on the right on wide screens, with a button next to the filter that switches to the list on top and the preview below, remembered in localStorage; narrow screens always stack them. The preview pane stays in place when the selection changes (the previous content stays, dimmed, until the next one loads; a placeholder shows when nothing is selected), and a splitter between the panes resizes them by drag or by arrow keys (15% to 85%; double-click or Home resets), with its position remembered in localStorage (per page kind) next to the orientation, which is one choice for both lists. (manual)
- **WEB-16** SHOULD — show "N of M" and a "Clear filters" link next to the filter while any filter is active, and colour only the state (a dot on its segment, the row border, the pill): the level badges differ by weight (MUST solid, SHOULD outlined, MAY plain), so red and amber mean the state alone. (manual)
- **WEB-17** SHOULD — drive the requirements filters from the keyboard when no field has focus: `1`–`7` pick a state, `S` and `L` step through the states and levels (`⇧` steps back), `0` clears every filter, `/` focuses the text filter; each control shows its key as a `kbd` hint and a tooltip lists the rest (`⇧S`), and the filter controls are radio groups where the left and right arrows move and select (one tab stop each). (manual)
- **WEB-18** SHOULD — navigate from a sidebar: the destinations grouped (Overview, Browse, Gaps) with an icon and a label each, and a control at the bottom that collapses it to an icon rail (tooltips keep the names; the choice is remembered in localStorage, and narrow screens start collapsed). On phones it becomes a strip of icons above the page. (manual)
- **WEB-19** SHOULD — on the Tests page show every detected test as a row (grouped by module, with its requirement IDs and its location) and, in the preview, the selected test: its name, location and module, the requirements it is tagged with (ID and text), and the source lines around it; the selection is in the URL (`?path=…&line=…`) and Esc clears it. A tag is evidence, not proof that the test passes. (manual)
- **WEB-20** SHOULD — on the Requirements page offer a View switch, list or documents (`?view=docs`): the documents view renders the chosen spec file (picked from a list of the files) in a single scrollable document pane, marks each requirement ID with its state, and scrolls to the requirement named in the URL. (manual)
- **WEB-21** MAY — build the dashboard from shared parts: one set of design tokens in `app.css` (type scale, spacing, accent tints and a tone attribute, `data-tone="ok|warn|bad|accent|muted"`, that colours pills, dots, badges, row edges and sections alike) and shared components for the split panes, the data table, the segmented control, the pill, the ID chip, the collapsible section and the preview heading. (manual)
- **WEB-22** SHOULD — mark what the working tree changed in the requirements, tests, specs and modules views (notes under the text of each affected requirement, `✎ spec edited`, `✎ src changed`, …, and on a file or module row a pill saying whether it is added, modified, deleted or renamed, or committed) and give each a "changed only" filter with its count, kept in the URL (`?changed=1`). (manual)
- **WEB-25** SHOULD — in a preview pane of a changed item (a requirement, a test, a spec file, the code viewer) offer an actual / diff switch: "diff" shows what exactly changed against HEAD, per file, with added and removed lines coloured and the hunk headers dimmed; the last choice is remembered in localStorage, and an item with no change shows the actual view without the switch. (manual)
- **WEB-23** SHOULD — offer a Changes page that shows every change in one place: the changed files, each marked added, modified, deleted or renamed (and whether staged), linked to the file viewer, the requirements they may affect (with their state), and the affected tests, specs and modules linking to their filtered views, with switches for staged only and untracked files; it says "working tree clean" when nothing changed and "not checked" without git. (manual)
- **WEB-26** SHOULD — let the Changes page choose what is compared (HEAD, the base branch, or one commit from the history of the commits not on the base branch, each marked committed), switch whitespace-only changes, ignored files and files spec17 does not scan on, show a deleted requirement as deleted and a rename with its old path, and name under each diff hunk the requirements it touches. (manual)
- **WEB-24** SHOULD — show a Changes card on the dashboard (changed files by added, modified and deleted, requirements affected and how many of them have no test) that links to the Changes page, with the affected count as a badge on the tab. (manual)
- **WEB-27** MUST — on connect ask `doctor` and `install_status`: Settings renders from those alone, never behind the scan, and a failed scan shows its error with a link to Settings instead of "Scanning…". (manual)
- **WEB-28** SHOULD — with no requirements, show a "no requirements yet" card on the dashboard (what a requirement line looks like, a link to Settings) in place of the 0% hero, still show the changes, the modules and the counts of source files, test files and detected tests, and say on the Requirements page that nothing was found. (manual)
- **WEB-29** SHOULD — on the Settings page, the CodeGraph card offers separate buttons to add its `.mcp.json` entry or remove it after a confirm. The card walks through install (commands and docs link when the binary is missing), connect (the add button) and index (`init` when there is none, `sync` whenever there is one, with how fresh it is). (manual)
- **WEB-30** SHOULD — make the rescan button run `codegraph refresh` (SETUP-08), which syncs whether or not a codegraph process runs, and then reload; a failed sync (a busy lock, say) shows codegraph's message and the reload still happens; the push and the 30-second reload never sync. (manual)
- **WEB-31** SHOULD — list a module's source files on its page, each linked to the code viewer. (manual)
- **WEB-32** SHOULD — on a first run, open Settings: with the dashboard open at the bare route, when the first scan found no requirements and the skill or the `.mcp.json` entry is not installed, or when a doctor check failed, replace the URL with `/settings` (Back still works). Nothing is stored: it stops once specs exist or both are installed. Never inside an MCP Apps host, which picks the view itself. (manual)
- **WEB-33** SHOULD — on the Changes page, order the sections commits (they define the scope), requirements that may be affected, then the changed files (with a commit selected, the titles of the last two carry its short hash), and list the requirements in the same table as the Requirements page (the same columns, cells, sortable headers, state-coloured row edge and review checkbox of WEB-35; no groups and no preview, a click opens the requirement), with what changed (`✎ src reached by a test`, `✎ spec edited`, …) as small notes under the text, in both tables, with the files in their tooltip. Reuse the requirement search, state, level and reviewed filters for affected requirements, including those reached only through tests. Filter those lists within the current comparison and keep the comparison when clearing the filters. (manual)
- **WEB-34** SHOULD — on the Changes page, let each of the Recent commits, Requirements that may be affected and Files sections collapse and expand from its header and resize vertically by dragging its bottom edge; each remembers per browser (localStorage) whether it is open and the height it was dragged to, a button on the header returns it to the automatic height, and without storage it still works with the defaults (open, as tall as its content). (manual)
- **WEB-35** SHOULD — let the reviewer mark a requirement reviewed from its row (a checkbox in the ID cell) on the Requirements and Changes pages (WEB-33): the flag is the requirement's commit from `commits` (API-15), kept per browser and repo in IndexedDB (database `spec17`, store `reviewed`, in memory when storage is blocked). A reviewed row keeps readable text and a visible reviewed marker; a requirement committed again since is unreviewed again (its tooltip says so), and one with uncommitted lines cannot be marked. A "Reviewed" filter (all / unreviewed, with the count, `?reviewed=0` in the URL) hides the reviewed ones, and shows only when git gave commits. (manual)
- **WEB-36** SHOULD — show who last changed what in the requirement preview, from `commits` and `blame` (API-15, API-16): under the spec location "last changed by AUTHOR, DATE" with the short sha and subject, and next to each tagged test the same for the line of its tag; the Tests page preview shows it for the selected test. Nothing is shown without git. (manual)
- **WEB-37** SHOULD — separate real changes from indirect ones: a requirement counts as changed (the Changes page list, its tab badge, the dashboard card, the "changed only" filters and the ✎ notes) when its bullet, a tagged test or a cited unit was edited (SCAN-32); one that is only "reached by a test" through the CodeGraph index (SCAN-22) is listed apart, collapsed, under "N more reached only through tests" on the Changes page. (manual)
- **WEB-38** MUST — Settings offers separate, confirmed actions to remove the spec17 skill or MCP entry in either the project or global scope (SETUP-12), shows the paths they affect, and refreshes their status after removal. A customised MCP entry can also be removed. (manual)
- **WEB-39** SHOULD — link each requirement table row with detected tagged tests to the Tests view filtered by its full requirement ID. Keep the filter in the URL and show a control to clear it. (manual)
- **WEB-40** MUST — for both the project and global scopes, Settings shows the skill, stdio MCP and HTTP MCP with individual statuses and install and remove actions (SETUP-13). MCP removal is confirmed and refreshes status (WEB-38). The dashboard directs users to Settings for these actions. (manual)
- **WEB-41** MUST — in each scope, Settings shows the installed stdio launch command and the configured HTTP MCP URL beneath their respective entries when `install_status` supplies those details (SETUP-14). Both are selectable, and paths with spaces in the command are quoted. Missing entries show no connection details. (manual)
- **WEB-42** MUST — Settings shows the version of the running spec17 server from `install_status`, matching the version printed by `--version`, including the commit and UTC build timestamp for a dev release (NFR-08). (manual)
- **WEB-43** SHOULD — use shared type tokens with a 14px default minimum for readable labels and 16px for requirement text. Keep search first on Requirements, Tests and Modules. Keep requirement search and its Filters disclosure on one toolbar row, with the filter options opening below it and an active count on the disclosure. On Tests and Modules, collapse secondary filters with an active count on narrow screens. Distinguish selected rows from hover and label tagged-test evidence explicitly. In requirement lists, show level and evidence state below the ID as compact labels in matching type, with lowercase levels on one line. Keep level and evidence colors consistent across themes, lists, filters and spec text. Give each colored pill its own title and tooltip. Explain only the active pill on hover, keyboard focus and tap, with Escape to dismiss. (manual)
- **WEB-44** SHOULD — open Settings with health checks and a read-only Run checks action. Lead with the verdict, tinted by its tone (green when every check passed, amber for warnings, red for failures) with the count of checks passed; show warnings and failures immediately and group passing checks in a disclosure. The Settings button in the header carries an amber or red badge while a check is not passing or the install is unfinished. Follow with agent setup for one selected scope (initially this repo), then optional CodeGraph management with index output beside its action. (manual)
- **WEB-45** SHOULD — wrap requirement links in the Tests table. On Overview and in the Tests table, use the shared requirement link to show a preview of up to three lines of spec text after a short hover or keyboard-focus delay, using already loaded data when available and fetching missing details on demand. Dismiss the tooltip on Escape. (manual)
- **WEB-46** SHOULD — keep the canvas module graph readable as it grows: spread connected modules according to graph density, fit the initial layout to the available canvas, and keep dependency arrows from becoming excessively thick when zoomed or heavily weighted. (manual)
